## R1 · On-chain program framework

- **Decision:** Rust program built with **Anchor 1.1.x (1.1.2)**, one program named `holdout`, deployed to **devnet**. Toolchain pinned to the Solana Foundation's tested combination: **Solana CLI 3.1.10**, Rust **≥ 1.89**, platform tools v1.52+, `solana-*` crates on `^3`, all `anchor-*` crates on the exact same version, `Cargo.lock` committed. Token CPIs go through Anchor's **token interface**, so the program works with either the classic SPL Token program or Token Extensions. The toolchain runs in **WSL2 (Ubuntu 24.04)** on the Windows development machine — Anchor 1.x binaries need GLIBC ≥ 2.39 and have no native Windows build.
- **Rationale:** Anchor 1.1.x (June 2026) is the Solana Foundation's recommended line for new projects (solana-dev skill, compatibility matrix). One program keeps account relationships, PDAs and invariants in one place for a 13-day build. SKR is an SPL asset; the mock SKR mint is a classic SPL mint, and the token interface keeps the door open for Token Extensions (the Genesis Token uses them).
- **Alternatives considered:** native Rust without Anchor (more boilerplate, slower to a correct IDL); several programs as in the archived PRD (cross-program invariants for no benefit); Pinocchio (less tooling, no time to absorb).

## R2 · Contract testing and clock control

- **Decision:** three layers, written **before** the logic they test (constitution VII):
  1. **Pure settlement math** in a dependency-free Rust module (`programs/holdout/src/math/`), unit-tested against every vector in PRD §19 (V1–V22) plus property tests for the arithmetic invariants.
  2. **Program integration tests** in **TypeScript on LiteSVM** (`litesvm` npm 1.3.x) through **`@solana/kit` with `@solana/kit-plugin-litesvm`**, using a **Codama-generated Kit client** rendered from the Anchor IDL. Tests set the Clock sysvar to jump to join cutoffs, deadlines and settlement. The randomised INV-1…INV-8 suite (acceptance criterion 7), including a 1,000-member cohort, runs here. A small **Surfpool** smoke suite (`anchor test`'s default runner in Anchor 1.x) exercises the real RPC path with `surfnet_timeTravel` before each devnet deploy. All of this runs in WSL2 — LiteSVM and Surfpool ship native binaries for Linux and macOS only.
  3. **Shared golden fixtures** (`fixtures/*.json`): account byte layouts, PDA derivations, instruction encodings and derived figures (breach, survivor counter, projected share) produced by the TypeScript tests and **replayed by the Kotlin `core` module's unit tests**, so the Kotlin client can never drift from the program.
- **Rationale:** LiteSVM runs in-process with clock control, and every rule here is time-driven; Anchor's TypeScript tooling is the most mature place to test the program itself. Golden fixtures turn "two languages" into one source of truth.
- **Alternatives considered:** `solana-test-validator` (slow, no clock control); `@solana/web3.js` v1 with the old Anchor TypeScript client (the Solana Foundation now recommends Kit; web3.js v1 is legacy); Rust-only integration tests (fine, but the generated Kit client makes fixture generation trivial); writing program tests in Kotlin (no LiteSVM bindings).
- **Deviation from the solana-dev skill, stated:** the skill says never to hand-write Borsh layouts for a program you own. Codama has no Kotlin renderer, so the Kotlin codecs in `core` are hand-written — which is exactly why they must replay the golden fixtures generated from the Codama TypeScript client and the real program (layer 3).

## R4 · On-device pose estimation and rep counting

> **Amended 2026-10-10 (analysis of PR #41).** The model, the runtime and the rule (FR-021) below still hold. Three things in this section were overtaken and are marked where they stand: the palm check is gone (2026-09-22, T047; `ReadyGate`, FR-020), angles are read in the picture rather than from world landmarks (002 research D1), and every sitting is counted at 45°, with the rule's own 160° as the top trigger and a top line set per sitting from the held arm (002 FR-001, FR-008, research D10). Spec 002 is the source for placement and the 45° rules. *(Review of PR #41: the Rationale, the placement's costs, the overlay, the model, the camera and spike S2 below carry notes too.)*

- **Decision:** **MediaPipe Tasks Vision — Pose Landmarker** (BlazePose GHUM, 33 landmarks, `LIVE_STREAM` mode, **FULL** variant on the **GPU delegate** with automatic CPU fallback, LITE if spike S2 misses 15 FPS on a Seeker) fed by **CameraX** `ImageAnalysis` (newest frame only, ~640×480). The rep rules, the pre-flight checks *(four when built; five pills since 2026-10-10 — the knees became their own gating check, 002 FR-024a)* and the palm check *(dropped 2026-09-22, T047: `ReadyGate`, the top of a push-up held about a second, took its place in the same module — FR-020, OD-3)* live in a **pure Kotlin/JVM module** (`kotlin/repcounter`) that consumes landmark frames and has no Android dependency.
- **How the angles are actually measured** — the part that decides whether the rule (FR-021) is enforceable:
  - **World landmarks, not image coordinates.** The task emits 3D world landmarks in metres relative to the hips, so elbow flexion and the shoulder–hip–ankle line stop depending on where the phone is lying. Image coordinates drive the overlay only. *(Superseded by 002 research D1: the app reads angles from the image landmarks, on the side nearer the lens at 45° (002 FR-009); world landmarks are used only where no image exists, which today means the synthetic traces.)*
  - **Smoothing before thresholding.** A one-euro filter on the landmarks feeding each angle. Published validation puts BlazePose's joint-angle error at roughly **2° mean absolute, RMSE ≈ 2.6°**, so raw per-frame angles cannot be compared against a hard edge.
  - **Hysteresis wider than that error.** The rule stays *top > 160°, bottom < 90°, body line ±10°, cycle 0.8–6 s* (FR-021), but the state machine triggers at **≥ 165° for the top and ≤ 85° for the bottom** by default *(at 45° — every sitting since 2026-10-08 — the top trigger is the rule's own 160°, and the sitting's top is the elbow held through the countdown less 10°, never below 148° (002 FR-008, data-model RepRules); the body line there is judged on the rep's median, refusing a fold below 140°, because ±10° cannot be measured at 45° — a weakness named in the README (002 Clarifications))*, so a 2–3° jitter band cannot flip a state or double-count a rep. A rep is counted by the state machine completing top → bottom → top, never by a single frame.
  - **Visibility gating.** Frames where elbow, shoulder, hip or ankle fall below the landmark presence threshold are dropped rather than scored; a run of dropped frames ends the attempt with the "can't see you" hint instead of guessing.
  - **Framing is classified, not required (corrected 2026-09-23).** This bullet previously read "a front-on phone cannot see elbow flexion at all", which contradicts the world-landmark bullet three lines above it and is wrong. The landmarks are 3D, so the angles are **geometrically recoverable from any view**. What changes with placement is *precision*: a single camera estimates depth far worse than position within the image, and a push-up seen head-on puts nearly all of its movement along the depth axis. Side-on keeps that movement in the image plane, which is the strongest signal; head-on leans on the weakest. Both are accepted — see the placement decision below. *(Superseded: see the note on that decision.)*
  - **Every number here is provisional until spike S2 measures it** against the 10 honest and 3 cheat videos; S2's deliverable is `fixtures/rep-traces/s2-angles.json`, the measured per-frame angle table the final thresholds are set from, committed with the traces so the tuning is evidence rather than recollection.
- **Rationale:** MediaPipe's Android task library with CameraX is Google's reference path, and the Hand Landmarker for palm liveness (R5) shares the same runtime and frame stream *(no longer: R5 was dropped on 2026-09-22 and no hand model ships)*. Keeping the rules in a JVM module makes them unit-testable against recorded traces — including deliberate cheats — without a phone. No part of the pipeline has a network path, so frames never leave the device (constitution X).
- **Alternatives considered:** ML Kit Pose Detection (fewer landmarks, no world coordinates); MoveNet Thunder via TFLite (17 keypoints, and the body-line rule needs hips and ankles; validation puts its upper-limb error under 10° RMSE, worse than BlazePose for this measurement); server inference (forbidden by constitution X).
- **Sources:** MediaPipe Pose Landmarker task documentation; BlazePose joint-angle validation (MAE ≈ 2.11°, RMSE ≈ 2.63°); MoveNet upper-limb range-of-motion validity study.

- **Which placement (decided 2026-09-23, after the first sitting):** **both.** *(Superseded by spec 002. Square side-on is accepted by no sitting (002 FR-003); head-on was retired for the Daily 25 on 2026-10-07 (002 FR-001), and since 2026-10-08 every sitting is counted at 45° in its stakes' band (002 research D10, 001 FR-021a). `Preflight.classifyView` still names the view, and the camera-view check now refuses any view the stakes do not accept (FR-019).)* People put the phone on the floor in front of them, and the pre-flight check that demanded a side-on view blocked the commonest placement, which is a check that stops the app working. `Preflight.classifyView` now names the view — `SIDE`, `OBLIQUE` or `FRONT` — from shoulder span against torso length in the image, a ratio that is independent of how the phone is rotated. The check fails only when it cannot tell what it is looking at.
  - **One rule set, for now.** `RepRules.forView` exists so spike S2 can give the front view its own triggers, and returns the same rules for every view today. *(Superseded: at 45° `forView` sets the top trigger to the rule's own 160°, and the counter lowers the sitting's top to the held arm less 10°, down to 148° (002 FR-008, revised 2026-10-01 by the product owner). ## R5 · Palm liveness

> **Dropped 2026-09-22** (T047; FR-020 amended, OD-3). Built, then removed after the first sitting on real hardware; `ReadyGate` replaced it and no hand model ships. Kept as the record of the decision.

- **Decision:** MediaPipe Tasks **Hand Landmarker** on the same CameraX stream: an open palm (five fingertips extended, palm facing the camera) held **3 continuous seconds**; **30-second timeout** back to pre-flight (FR-020). The hand model runs only during the liveness step and is closed before counting, so pose inference has the GPU to itself. *Confirm at spike S2.*
- **Rationale:** same runtime, same frames; hand landmarks make "open palm facing the camera" a geometric rule in `repcounter` rather than a trained classifier.
- **Alternatives considered:** pose wrist/hand landmarks only (too coarse to tell an open palm from a fist).

## R6 · Banked progress and pending submissions on the device

- **Decision:** **MMKV for Android** key-value storage. Keys are scoped by **wallet + cohort (or `challenge`) + day index**, so another wallet's or another day's progress is never read and expires by construction at the boundary. A block is **written synchronously before** the UI shows it as banked. A completed cohort day not yet landed is stored as a **pending submission** `{cohort, dayIndex, proofHash, completedAt}` and shown as "Done — tap to submit" (Phase 1). The daily streak is stored the same way, per wallet.
- **Rationale:** MMKV writes are synchronous and survive process death — the "write before showing banked" guarantee (FR-023) — with no server (FR-024a).
- **Alternatives considered:** Jetpack DataStore (asynchronous writes — a crash between count and write could show an unsaved block); Room (more setup than a handful of keys needs).
- **Resolves:** P10.

## R7 · Time on the device

- **Decision:** every deadline, breach, lock and countdown is computed from **chain time** — the `unix_timestamp` in the Clock sysvar — read on app start, on resume, and after each confirmed transaction, then advanced with **`SystemClock.elapsedRealtime()`** (monotonic) between reads. The device wall clock is never used. Formulas live once in `kotlin/core` (`Derive.kt`), shared by app and crank and pinned by golden fixtures (R2).
- **Rationale:** FR-017 and constitution II make chain time the only judge; a monotonic timer can't be moved by changing the phone's clock, and periodic re-sync bounds drift to seconds.
- **Alternatives considered:** device clock (manipulable); a time server (a server, and still not chain time); **evaluating deadlines in a backend**, rejected 2026-09-15. A backend knows nothing the contract does not, so moving the decision only changes who is believed. One that decides outcomes can forfeit every member but one account, which then claims the whole pool legitimately, so a stolen key empties cohorts without touching a withdrawal function. It enters the hot path of every sitting, because it must then accept submissions too. And a dead backend at a boundary destroys the only record of who made it, where a dead keeper only delays money.
- **If per-member local midnight is ever required** (a global launch, spec OD-1): the safe pattern is a **bounded oracle**. The backend may only assert a miss inside the window between the earliest possible deadline (UTC+14) and the latest (UTC−12), both of which the contract computes itself; outside that window the contract refuses early claims and forfeits late ones on its own. That caps the backend's discretion at 26 hours and makes a fabricated winner impossible. Moved here on 2026-10-10 from D-B of the retired scope document (`git show 7dc976a:docs/holdout_scope_and_state_machines.md`).

## R8 · Reading chain state at 1,000 members

- **Decision:** the app reads program accounts directly from a **devnet RPC endpoint** that supports `getProgramAccounts` filters (a hosted devnet RPC provider, with public devnet as fallback): memberships of one cohort via a `memcmp` filter on the cohort key and a `dataSlice` covering only the fields the roster and counters need; decoded in `core`, cached in memory, refreshed on resume and — *as built (PR #62 review, 2026-10-12)* — on this cadence: the app-level Standing loop is the only loop on the running Holdout's roster, every 30 seconds wherever the member is (Today's, the Holdouts root's — `TabRoots.watchedOnHoldouts` — and its own detail screen leave it to that loop); a finished Holdout is read every 10 minutes while its screen is not shown (`TabRoots.rosterEveryMillis`); a detail screen keeps its own 30-second loop on any other Holdout, and on a finished one while it is shown, and `RosterLoop` skips an address the app loop already covers (`rosterReadByApp`). `HoldoutViewModel.loadRoster` allows one read per cohort in flight — a read still out answers any asked meanwhile (the schedule, a screen opened twice) — and gives a read up after 60 seconds; a "Check again" (spec 005) forces a read of its own, since one already out may be hanging. **No Holdout server or indexer.** Phase 2 league leaderboards read `Profile` accounts the same way.
- **As built 2026-10-13 (FR-071, Session 2026-10-13):** the snapshot's own reads are budgeted. `ChainRepository` asks each failed snapshot call once more after 1.5 s (`RETRY_MILLIS`) before the read gives up; keeps `Config` and the leagues for 10 minutes (`SETTINGS_MAX_AGE_MILLIS`), reading the leagues sooner when a cohort names a league not read yet or any cohort's settlement fields moved (`counted`, `settled`, `noFinisherBoost`, `boostReceived`, `comebackOwed`, `comebackFunded`, `comebackClaimed` — `settlementOf`, `f05158c`: `settle_count` moves the reserves the screens show page by page, before `settled`). It gives the leaderboard its snapshot's cohorts read as the read before the profiles when it is at most 30 s old (`COHORTS_REUSE_MILLIS`) — the read after them stays. *Known limit:* a comeback released on its own (`release_comeback`, FR-037h) moves `comeback_reserve` to `boost_reserve` without changing any cohort, so the projected boost shown can lag it by up to 10 minutes, the leagues' age limit — catching it would mean reading the leagues every pass, which the 10-minute rule declines; the projected boost is an estimate (FR-037d) and payouts are computed on chain. `HoldoutViewModel` sets `offline` only after `OFFLINE_AFTER_FAILED_READS` = 2 snapshot reads in a row fail (the first, with no view yet), keeping the last view meanwhile; only the 30-second pass joins a snapshot read already out for the same wallet (a Check again's included), waiting at most `JOIN_READ_MILLIS` = 60 s, while a Check again, the read closing an action and the network-return read always start their own — a read started earlier, maybe while the chain was down, cannot answer for them (`a995bcf`). `loadRoster` and `loadLeaderboard` skip a read while the last answer is under `MIN_READ_AGE_MILLIS` = 20 s (a forced roster read — Check again — excepted); one leaderboard read at a time, every `LEADERBOARD_REFRESH_MILLIS` = 90 s while the boards are open (`shell/Shared.kt`). A pass on an answering node: cohorts, the wallet's memberships, profile, SKR and SOL — five calls, down from seven. *(Its cadence — the snapshot, `Config` and memberships every 30 s or 10 minutes, the leaderboard every 90 s — is superseded by the next bullet: reads by change.)* *Alternatives considered:* keeping the last `ChainView` on the phone and showing it marked stale after the process dies (deferred: every snapshot type would need a stored form); a timeout on the snapshot read itself (rejected: the HTTP client already bounds a call, and a cap that retries turned an unanswered read into an endless loop under test).
- **As built 2026-10-13, reads by change (FR-071 as amended the same day; `492f60b`):** a pulse reads only what moves on its own, and keeps the rest until the counters that move it do. `Rpc.multipleAccounts` reads up to 100 accounts in one `getMultipleAccounts`, each with its data and lamports. `ChainRepository` reads, each pulse, only the cohorts not settled yet (`Rpc.unsettledCohorts`, `settled = 0`) and keeps the settled ones (`KeptCohorts`): one that leaves the not-settled list is fetched once through `multipleAccounts`, and all cohorts are read whole every 10 minutes (`FULL_READ_MILLIS`) — the all-cohorts read would otherwise grow with every 10-minute Hackathon round. The wallet's profile PDA, SKR account and the wallet itself (its SOL, from lamports) are one `multipleAccounts` call. Its memberships (`KeptMemberships`) are read again when the counters of a cohort it is in move (`Holdout.countersOf`: member count, forfeits recorded, members counted, settled — a submit moves none), after 5 minutes (`MEMBERSHIPS_MAX_AGE_MILLIS`), or by `ChainReads.loadFresh`, which `act`, `checkNow` and the network's return use and which also re-fetches the wallet's own settled cohorts. While a send may still land (`UiState.pending` not empty), `HoldoutViewModel.read` uses `loadFresh` for every read, pulses included (`c8ea85c`, Codex P1 on #72): a submit or a claim moves no cohort counter, so a kept membership would settle it as unlanded once its 120 s window passed. `Config` is kept an hour (`CONFIG_MAX_AGE_MILLIS`); the leagues as in the bullet above. `HoldoutViewModel.setLive`, fed from `NavState.showsLiveChain` (`HoldoutApp`), holds the pulse while Me, About, the tour or a sitting is in front; a live screen back after the pulse's wait reads at once. After failed reads the pulse waits `pulseWait()` = 30, 60, 120, 240 s, at most `MAX_BACKOFF_MILLIS` = 5 minutes; an answer after failures wakes it to start its wait over. `loadRoster(maxAgeMillis)` reads when the cohort's counters differ from those at its last answer (`rosterCounters`) or the answer is `maxAgeMillis` old — `TabRoots.rosterEveryMillis`: 30 s for a Running Holdout, 10 minutes otherwise — the loops only looking every 30 s; `loadLeaderboard` reads when any cohort's forfeits recorded or settlement (`boardCounters`) moved or after 10 minutes (`BOARD_MAX_AGE_MILLIS`), `LEADERBOARD_REFRESH_MILLIS` now the 30 s look. The 20-second minimum age stays. A steady pulse with a wallet is **two calls**, down from five; no chain state (snapshot, rosters, boards) is read on Me, About, the tour or a sitting — only chain time every 10 minutes (R7), and a Holdout day's sitting that finishes while the chain can't be reached checks once — so Me's balances and badge are as of the last read. *Known limit:* settled cohorts are kept up to `FULL_READ_MILLIS` (10 minutes), so another member's `claim_payout` on a settled cohort (its `pool`, `held_stake`, `comeback_claimed`) shows at the next full read; the wallet's own claim re-fetches its settled cohort at once through `loadFresh`. *Alternatives considered:* `accountSubscribe`/`programSubscribe` over WebSocket (deferred to its own step, with polling kept as the fallback); reading the leagues every pulse to catch a standalone comeback release (declined, see the known limit above).
- **Rationale:** a 1,000-member cohort is ~100 KB of membership data — one call. The RPC node is chain infrastructure, not a Holdout service that decides or ranks anything (FR-060, FR-065).
- **Alternatives considered:** a Holdout indexer (a server that could show unsupported figures); one websocket subscription per membership (1,000 subscriptions).
- **Resolves:** P8.

## R9 · Paging automation for 1,000-member cohorts

- **Decision:** `record_forfeits`, `settle_count` and `open_cohort` are **permissionless**. Paged instructions take **(membership, profile) pairs in remaining accounts, up to 10 pairs per transaction** (tuned at spike S3 against the transaction size limit). Each membership carries its own processed flag, so pages can run **in any order and any number of times**. Settlement is split into `settle_count` (paged, order-independent; forfeits any still-unrecorded breach in the page first) and `settle_finalize` (one transaction, only once every member is counted).
- **Rationale:** per-membership flags make idempotency and out-of-order paging structural rather than a cursor that must be advanced correctly (constitution VIII, acceptance criterion 7). A 1,000-member cohort needs ~100 short transactions per step — minutes for the crank, and anyone can run them.
- **Alternatives considered:** a stored cursor (a crashed caller must resume exactly; two callers race); address lookup tables for bigger pages (unnecessary at this scale; revisit if S3 shows limits bite).

## R10 · Exact settlement in constant time

- **Decision:** because every stake in a cohort equals one of that cohort's **four** locked chip amounts (FR-055), `settle_count` accumulates **finisher counts per tier** alongside `total_finisher_stake` (`T`). `settle_finalize` computes, in constant time:
  - `share_t = floor(pool × chip_t ÷ T)` for each tier `t`
  - `remainder = pool − Σ_t count_t × share_t`, sent to the fee destination (FR-032a)
  - with `T = 0`: `developer = floor(pool ÷ 2)` to the developer destination and `pool − developer` to the operations destination; nothing carries over (FR-037, revised 2026-10-05 and 2026-10-09)
  A claim pays `stake + share_tier`, read from the finalized cohort.
- **Rationale:** the exact remainder normally needs every finisher's share; tier counters make it O(1) and give every member of a tier a byte-identical payout (acceptance criterion 3) with no iteration at claim.
- **Alternatives considered:** storing each finisher's payout during counting (the pool isn't final until every forfeit is recorded); leaving the remainder in the pool (rejected by H11).

## R11 · Opening cohorts on schedule

- **Decision:** each league has a `LeagueConfig` holding `first_start` (a Monday 05:00 UTC), `cadence` (7 days), `duration_days`, `reps_per_day`, `day_length` and `next_index`. Cohort `i` starts at `first_start + i × cadence`, join cutoff `start − 3,600 s`. `open_cohort` is permissionless and succeeds only for `i == next_index` and, for `i > 0`, only once cohort `i − 1` has started; it copies the current chip set. **Test leagues** with non-default `day_length` are created only by the admin, only in builds with the `test-leagues` feature, and used on LiteSVM and — *amended 2026-09-26, constitution v1.4.0* — on the devnet program itself, which is built with `test-leagues` so that **one disclosed short test cohort** can run the whole cycle before the deadline and be recorded for the walkthrough and demo video (FR-044, FR-044a). It is labelled everywhere in the app and keeps its progress in the profile's test slot, apart from judged progress. Mainnet builds never carry the feature. The judged leagues start **Monday 5 October 05:00 UTC** (moved from 28 September).
- **Rationale:** the schedule is pure arithmetic on stored parameters, so no caller can pick a start time or chip set (FR-030a), and a late opening still yields the scheduled start (ES-15).
- **Alternatives considered:** the Operator passing start times (a privileged, error-prone input); cron-only opening (a dead crank would stop the league).

## R13 · Faucet design, including a zero-SOL wallet

- **Problem found in planning:** a brand-new wallet with **0 SOL cannot pay the fee** for any transaction, including its own faucet claim, and a program-derived address cannot pay transaction fees.
- **Decision:**
  - **Test SKR** is minted per claim by the program: the mock SKR mint's authority is a program address (`["mint_authority"]`), so the faucet never runs out of SKR. Amount: the current chip set's **$100-tier** amount.
  - **Devnet SOL** comes from a program-owned **faucet vault** (`["faucet_vault"]`), funded to last from submission through 11 November 2026. A claim **tops the recipient up to 0.02 SOL** — enough for membership and profile rent plus every fee of a 21-day cycle — and sends nothing if they already hold that much.
  - **Fee bootstrap:** the app bundles a **devnet sponsor key** whose only use is paying the fee for `claim_faucet`. The instruction needs **no member signature** — the recipient is the connected wallet's address — so no partial signing through MWA is involved, and it reimburses the sponsor's fee and rent from the vault in the same instruction, so the sponsor's balance stays flat. A wallet that already holds SOL may pay for its own claim instead; `claim_faucet` accepts either payer.
  - **The sponsor's float is small and refillable by anyone (added 2026-09-19):** the bundled key holds a float of `Config.faucet.sponsor_float` = **0.05 SOL** and nothing else. Because anyone can extract the key, anyone can also empty that float with a plain System Program transfer — no faucet guard can prevent it, and an empty sponsor cannot pay a claim fee, which would end zero-SOL onboarding rather than merely costing a day's allowance. So a **permissionless `top_up_sponsor`** refills the float from the faucet vault whenever the sponsor holds less than half of it, charged against the same daily budget as a claim. The crank runs it on every 10-minute pass, and any wallet with a little devnet SOL can run it too. A drain therefore pauses zero-SOL onboarding for at most one crank pass, needs no Operator, and costs the vault no more than the day's budget (FR-042b).
  - **What a refused refill means:** `top_up_sponsor` fails while the sponsor still holds half its float (`SponsorFloatSufficient`) and once the day's budget is spent (`FaucetCapReached`). Both are ordinary outcomes, not incidents: the crank reports them, exits `0` and tries again on the next pass. **No separate per-day refill counter is stored** — refills draw on the same lamport budget as claims, which is what bounds the day, and a second counter would only bound it twice while adding state and another way to be wrong.
  - **Limits enforced on-chain (revised 2026-09-19 — a lamport budget, not a claim counter):** *(2026-10-12: the former once-per-recipient-per-day rule, `Profile.last_faucet_day < today`, is removed — the product owner asked for the limit to go on devnet; `last_faucet_day` is still stamped but nothing reads it, and `FaucetAlreadyClaimedToday` 6050 stays in the IDL, never raised. The daily budget below is now the only abuse guard: repeated claims by one wallet cost the vault only what they move, and a wallet already holding the top-up moves no lamports.)* a **daily budget of 0.72 SOL on every lamport that leaves the faucet vault** — recipient top-ups, sponsor fee and rent reimbursements, and `top_up_sponsor` refills alike. Counting claims was not enough: a recipient already holding 0.02 SOL needs no top-up, so under a claim counter the rent and fee reimbursed for its brand-new `Profile` and token account left the vault uncapped, and the same recycled 0.02 SOL could pay the account-creation costs of fresh wallet after fresh wallet. Budgeting lamports closes that and keeps one day's abuse at ≈ 0.72 SOL however it is spent. A claim that moves no lamports at all — the recipient pays its own fee and already holds the top-up, as every scripted wallet does (R12) — consumes none of the budget and is not capped. When the budget or the vault is exhausted, `claim_faucet` fails with a specific error and the app shows ES-0b.
  - **Scripted wallets** are pre-funded with SOL once by the Operator and pay their own fees, so their claims mint SKR only (R12).
  - **Sizing (revised 2026-09-17 for the live period through 11 November; the stored values are normative in data-model §1.1):**
    - **Worst case per SOL-paying claim ≈ 0.024 SOL:** the 0.02 top-up, plus the profile and SKR token account rent reimbursed to the sponsor for a brand-new wallet.
    - **Funding deadline:** the vault may be topped up by hand until submission. From 13 October (moved from 9 October, 2026-10-09) it must last to 11 November with no top-up (FR-042a).
    - **Amount:** 34 days × 0.72 SOL ≈ **24.5 SOL**, so the vault is funded to **25 SOL by 12 October** (was 8 October; the live period is now 30 days, so 25 SOL leaves more margin).
    - **Why 0.72 SOL a day is enough:** at the worst case it is 30 brand-new wallets a day, well above expected judge and community traffic, and one claim funds a wallet for a whole 21-day cycle. Refilling a drained sponsor draws on the same budget, so a griefer must spend the whole day's allowance to stop onboarding for the rest of that day.
- **Rationale:** meets FR-042a and FR-042b — no server, no public faucet, no manual top-up — within Solana's fee rules. A sponsor key in the APK is a devnet-only trust gap: anyone can extract it, but it holds only a 0.05 SOL float, cannot touch a stake, a pool or a carry-over, cannot be locked out of use because anyone may refill it, and the daily lamport budget bounds what it can cost in a day.
- **Must be documented** in the README's known weaknesses (constitution XI): "the faucet's fee sponsor key ships in the app; a daily lamport budget caps abuse at one day's faucet allowance, and anyone can refill the sponsor if it is drained."
- **Alternatives considered:**
  - **The public devnet `requestAirdrop` for the first SOL.** Rate-limited and often failing — the reason H22 exists.
  - **A relayer server that co-signs.** A server, rejected by H22.
  - **Requiring members to bring devnet SOL.** Breaks FR-042a.
  - **Keeping the cap at 60 a day.** About 49 SOL for the longer live period.
  - **A claim counter as the only cap** (the plan until 2026-09-19). Left every reimbursement that needed no top-up outside the cap.
  - **Leaving a drained sponsor to the Operator.** Manual intervention during the live period, which FR-042a forbids.
  - **Making the recipient always pay its own claim fee.** That is exactly the zero-SOL case the faucet exists for.
  - **A larger sponsor float, refilled by hand.** More to steal and nothing gained: the float only has to cover the fees between two crank passes.
  - **A smaller 0.01 SOL top-up to stretch the vault.** Wallets may add priority fees to member transactions, and 21 days of them could exceed it.
- **Resolves:** P11.

## R14 · Fee destination and privileged keys

- **Decision:**
  - `Config.fee_destination` is the **operations** destination: an SKR token account owned by the treasury wallet, set at initialisation. `Config.developer_destination` is the **developer** destination, set at the same time and named in the README with what each is for (FR-037f). The 30 % fee on a forfeited stake is split by program rule — 10 % pledged to the forfeiting member's comeback (kept in the cohort vault until the forfeit is counted, then moved to the league's reserve vault), 10 % to the developer destination, 10 % to operations (FR-027, H35; re-split 2026-10-09 and again 2026-10-12, R24) — and operations also receives the rounding remainders (FR-032a). A no-finisher pool no longer reaches either destination: it goes to the league's boost reserve (FR-037, R24).
  - `Config.operator` may only `publish_chip_set`.
  - `Config.admin` may only `initialize`, `create_league` and `set_flags` (the genesis gate). `create_league` creates the two real leagues at launch, and a `league_id ≥ 100` test league only in builds carrying the `test-leagues` feature — one instruction, not two.
  - **Who may `initialize` (added 2026-09-19):** the program's **upgrade authority**, verified inside the instruction against the program's `ProgramData` account, and it becomes `Config.admin`. Before `Config` exists there is no stored key to check a signer against, so a deployment left uninitialised for even a moment could be claimed by a stranger who would then hold `admin`, `operator`, `sponsor` and the fee destination — and the program ID, which the app and the README both name, could not be reclaimed. Binding to the upgrade authority needs no constant in the source, works the same on any deployment, and on the one devnet program, and anyone can verify it from chain state. **Ordering consequence:** `initialize` must run before the authority is revoked (FR-007b, README weakness); revoking first would leave the program permanently uninitialisable. Rejected: a hardcoded admin pubkey (a constant to keep in step with the deployed program's authority, and it leaks a key into the source); trusting the deploy-then-init window to be short (it is a race the attacker picks the timing of).
  - **No instruction** lets any key move a held stake, a pool or a carry-over except the rule-driven instructions in `contracts/program-instructions.md`.
  - **Program upgrade authority** (added 2026-09-17, FR-007b) is held by the admin key and kept through the live period, used only to deploy defect fixes.
    - An upgrade never changes an existing account layout, a rule an existing cohort runs under, or any fund movement; a fix that would need any of those is not deployed.
    - The README names the authority as a known weakness, with its fix: revoke it once the contract is final.
    - Rejected: revoking it at the freeze. A defect found after 28 September would be unfixable while cohort #3 carries the walkthrough.
- **Rationale:** constitution I — the contract is the only authority on funds; the only discretionary powers are the chip set and the documented flags.
- **Alternatives considered:** fees to a program-owned treasury (nobody can spend them; nothing gained); an admin rescue withdrawal (violates constitution I).
- **Resolves:** P4.

## R15 · Chip set tooling (Phase 1 and 2)

- **Decision:**
  - **Phase 1:** `crank chips publish --rate <USD per SKR>` converts $10/$25/$50/$100 to SKR base units, rounded **down to the nearest 10 whole SKR** (minimum 10 SKR), and sends `publish_chip_set` once at launch. The rate is read by hand from a public SKR market price on launch day and recorded in the README — **never on-chain**, so the contract holds no fiat figure at all.
  - **Phase 2** *(decided 2026-10-06)*: `crank chips publish --auto`, a **standalone Operator command** run **every hour** by the Operator's OS scheduler, in any time zone (amended 2026-10-07) — never inside `crank run`, so the Operator key is loaded only for that run. The rate comes from the **Jupiter Price API only** (keyless, by the mainnet SKR mint); with no rate it exits without publishing (FR-057). It **re-prices every week** from that rate — no drift threshold, and a new version even when the rounded amounts are unchanged (the threshold, measured on the $100 tier, was dropped the same day). It publishes **at most once per publish window** *(amended 2026-10-10)* — the 4 hours before each Monday 05:00 UTC boundary, by chain time: a run outside it, or a `Config.chip_published_at` already inside it, means nothing to do. The first hourly run inside the window publishes; a run that fails or finds no rate is retried by the next one inside it. The cohorts opening at the boundary copy that set, so they lock a rate at most 4 hours old; publishing on the first run *after* 05:00, as first built, reached only the following week's cohorts. No send starts in the window's last 90 seconds — about a blockhash's life, and the send is watched for 60 s — and the chain's time is read again just before sending, since the rate fetch can take 30 s: a set landing after 05:00 would likewise reach only the next week's cohorts *(added 2026-10-10, PR #30 review)*. A blockhash lasts about 150 blocks, not a fixed time, so the cutoff alone could not promise that; `publish_chip_set` therefore carries a deadline, `valid_until`, and refuses a set at or after it (`ChipSetExpired`, 6014): the weekly re-price signs the window's close, a hand publish chain time + 10 minutes unless `--valid-until` says otherwise. A time, never a price (constitution III). Hourly, not once on Monday, because `CRON_TZ` is not portable (Debian cron ignores it) and a local-time Monday run can land before 05:00 UTC or shift with daylight saving. Two overlapping runs could both publish before either lands; with one Operator key the worst case is a near-identical duplicate set that week, so the race is accepted rather than closed with a program change.
- **Faucet interaction (added 2026-09-19):** a re-price may lower the tiers while a cohort that copied the older, larger set is still open. `Config.chip_set.max_top_tier` is therefore a high-water mark — `max` of every `amounts[3]` ever published — and the faucet mints that rather than today's top tier. Since no cohort can be created before a chip set exists (FR-055b) and the mark never decreases, it is at least the top tier of every cohort that exists, so FR-042a holds whatever order publishing and opening happen in. Minting more than today's tier costs nothing: the program mints mock SKR per claim.
- **Rationale:** readable amounts; the contract never sees a price (constitution III); Phase 2 is pure tooling on an instruction Phase 1 already has.
- **Alternatives considered:** an on-chain oracle (forbidden by constitution III).
- **Resolves:** P3.

## R16 · Completed-day proof

- **Decision:** `submit_day` is signed by the member's wallet through MWA and carries a 32-byte `proof_hash` — SHA-256 of the day's verification summary (day index, rep count, block times, sitting count, model version). The hash is emitted in the `DayCompleted` event, not stored in an account.
- **Rationale:** matches scope doc D-E (client-signed, documented trust gap) at zero storage cost; a future attestation signer can check traces without a migration.
- **Alternatives considered:** an attestation account per day (rent for 21 days × 1,000 members, for a hash nothing verifies on devnet).

## R17 · Seeker Genesis Token gate — contract at mainnet, app on devnet *(revised 2026-10-10, H38)*

Staked Holdouts are Seeker-exclusive (spec FR-003b–FR-003d, constitution v2.3.0). Until this revision the check was described here but never written: `join_cohort` passed `holds_genesis = false`, so turning the flag on would have closed joining to every wallet.

**The token** (Solana Mobile docs, *Seeker Genesis Token*): a Token-2022 (Token Extensions) NFT, one per device, minted into the Seed Vault wallet's primary account. Its mint carries a **Metadata Pointer** and a **Token Group Member** extension; the group, which is also the metadata address, is **`GT22s89nU4iWFkNXj1Bw6uYhJJWDRPpShHt4Bk8f99Te`** (mint authority `GT2zuHVaZQYZSyQMgJPLzvkmyztfyXg2NJunqFp4p3A4`). A wallet holds one when a Token-2022 account it owns has **amount > 0** and a mint whose `TokenGroupMember.group` is that group; an emptied account stays behind after a transfer, so amount 0 never counts. A group member can only be initialised with the group's update authority signing, so no one can mint a token that claims the real group.

- **Decision — contract (mainnet):** with `genesis_gate_enabled` on, `join_cohort` reads two **remaining accounts**, `[member's Token-2022 token account, its mint]`, and accepts the join only if both are owned by the Token-2022 program, the token account's owner is the member, its mint is the second account, its amount is ≥ 1, and the mint's `TokenGroupMember` extension names the group above. Anything else — missing accounts, a wrong owner, an empty account, no extension, another group — fails with **6024 `GenesisGateClosed`**. With the flag off nothing is read and nothing is required. The group is a **compile-time constant** (`SEEKER_GENESIS_GROUP`), not a `Config` field: it is a fact of the Seeker, not a parameter, and leaving `Config` alone keeps its layout, the IDL and every client unchanged. The verification is a pure helper over the two accounts' bytes, unit-tested in Rust with crafted mints (the real group passes; a fake group, no extension, amount 0, another owner and SPL-Token ownership fail), and the LiteSVM suite injects a token account and a mint carrying the real group's member extension — LiteSVM writes accounts directly, so no group authority is needed — to show a join with the flag on succeeding with it and failing without it.
- **Decision — app (devnet):** Seeker Genesis Tokens exist only on mainnet, so the devnet flag stays off and the member app checks before it offers to sign a join. It reads the connected wallet's address — the same key on both networks — from the **names endpoint** (`holdout.namesRpcUrl`, Solana mainnet, spec 003): `getTokenAccountsByOwner` with the Token-2022 program id and `jsonParsed`, keeps accounts with amount > 0, then `getMultipleAccounts` (`jsonParsed`) on their mints and looks for a `tokenGroupMember` extension whose `group` is the constant. The reader is a new `SeekerGenesisReader` in `kotlin/core`, built like `SeekerNameReader`: mainnet, read-only, unable to sign or send. It answers **Holds**, **None** or **Unknown** (refused, failed, rate-limited or too slow — a check that has not finished after **10 s**, `GENESIS_TIMEOUT_MILLIS`, is Unknown). Only **None** shows the Seeker-exclusive notice; **Unknown** refuses the join with the try-again message (FR-003d). A **Holds** answer — mint, when, and the token account — is remembered per wallet in MMKV (`seeker:{wallet}`, data-model §4) and never re-asked, so a confirmed owner is not blocked by a later outage; **None** is never remembered, so a wallet that gains a token is let in on its next try. Leaving, submitting and claiming are never checked.
- **Rationale:** the contract check is the one that cannot be bypassed, and it is ready the day the program reaches mainnet; on devnet the app is the only place the mainnet token can be seen. Remaining accounts keep the hackathon build's interface exactly as it is: no account is added to the IDL, the Codama client, `instructions.json` or Kotlin's instruction builder, and a client that never sends them behaves as before while the flag is off.
- **Debug bypass, for local runs:** the Gradle property `holdout.seekerGate=off` turns the app check off in **debug builds only** (a `BuildConfig` flag that release builds always set on), so the emulator, a local validator (quickstart §5a) and a tester's plain phone can still reach the stake confirm. A release build always checks.
- **What mainnet launch still needs from the client:** turning the flag on is not enough by itself. The app's join must then send the member's Seeker Genesis Token account and its mint as `join_cohort`'s remaining accounts (Kotlin `Instructions.joinCohort` and the crank's scripted joins send none today, which is right while the flag is off), so `SeekerGenesisReader` returns the **token account as well as the mint**, ready for that. Until the client sends them, `set_flags(true)` would refuse every app join with 6024 — the README's fix says both steps.
- **Known weakness (README, constitution XI):** on devnet the gate is the app's, so a wallet that signs a join without the app is not stopped. Fix: the contract check, on at mainnet launch. A Holds answer is remembered on the phone, so a token later moved to another account of the same Seed Vault still lets the old wallet join from that phone; the contract check closes that too.
- **Alternatives considered:** a `Config.genesis_group` field (a layout change, a new `initialize`/`set_flags` parameter and a client change for a value that never changes); two `Option` accounts on `join_cohort` (an IDL and client change in every language two days before submission); turning the flag on on devnet with a devnet stand-in group issued by the admin (needs an issuing step per member and per judge); leaving exclusivity to the pitch alone (the flag rule forbids a flag with no logic behind it); checking every time with nothing remembered (blocks a real owner on every outage); letting a join through when mainnet cannot be reached (breaks the exclusivity claim).

## R21 · On-device reminders (added 2026-09-27)

- **Decision:** reminders (FR-068) are **local notifications scheduled by the app with `AlarmManager`**, no server:
  - **Clock:** alarms are set on `ELAPSED_REALTIME_WAKEUP`, converted from the cohort's chain-time instants through the same `ChainClock` reading the screens use (R7) — so the device's wall clock never decides when a reminder fires (FR-017, constitution VI).
  - **Precision:** `setWindow` with a bounded window — a third of the lead, at least the 10 minutes Android allows without the exact-alarm permission — so a reminder always arrives before its deadline: 15 to 5 minutes before a one-hour day's, 3 to 2 hours before a 24-hour day's. A 10-minute test day (H32, 2026-09-29) is reminded as it opens, and the reminder may come at any point of the day. *(Changed 2026-09-27: `setAndAllowWhileIdle` let the Seeker hold a reminder about 57 minutes, past a one-hour deadline.) Doze holds a `setWindow` alarm until its next maintenance window, so each reminder is **also** set with `setAndAllowWhileIdle`, which Doze lets through, later; whichever fires first posts, the other stays quiet, and a reminder whose deadline has already passed posts nothing. An idle phone may therefore still get a reminder late, or not before the deadline. *(Amended 2026-10-11.)* The **Midday** reminder is set the same way, with the same window as the Deadline one (`windowMillis(day length)`: an hour for a 24-hour day, so it arrives 17:00–18:00 UTC) and the same `setAndAllowWhileIdle` fallback for an idle phone, which may bring it later; the rule is "a day of 12 hours or more" (`MIDDAY_MIN_DAY_SECONDS`), not "a 24-hour day". No `SCHEDULE_EXACT_ALARM`: that is a special permission the member would have to grant in settings, for a reminder that is a courtesy (FR-068a).
  - **What is scheduled:** the start of each Holdout the member holds a place in, and for every day not yet on chain, `deadline − min(3 h, max(day length ÷ 4, 10 min), day length − 1 s)` — for a 10-minute day, as it opens; its first day is left to the start reminder. The schedule is **recomputed from chain state on every refresh** (R8) and on app start: joins, leaves, completed days and forfeits simply change what the next computation produces — there is no separate schedule to keep in sync. Past instants are skipped. *(Amended 2026-10-10, FR-068.)* A day of 12 hours or more also gets a **Midday** reminder at `deadline − day length ÷ 2` — 17:00 UTC for a 24-hour day, an evening in Europe and a working day in the Americas — posted on the sounding channel, and its **Deadline** reminder is then posted on a second, **silent** channel (`IMPORTANCE_LOW`: no sound, no vibration, shown in the shade), because 3 hours before 05:00 UTC is the middle of the night in Europe. Shorter days keep their one sounding reminder. Chain time only; no timezone or locale (constitution II). *(Amended 2026-10-11.)* Three rules keep these apart: **one rule for silence**, `Reminders.isSilent(kind, day length)` — a long day's Deadline reminder, a long-day Holdout's Finished notice (FR-068b) and every NotSent notice — which core and the receiver both call; **one notification per Holdout day**, `Reminders.notificationId`, so that day's Midday, Deadline and NotSent notices replace one another in the shade rather than stack beside it (the start keeps its own); and **alarm ids that cannot collide**, `(cohort hash × 256 + day) × 64 + slot`, the slot being the kind's ordinal or `5 + tick` (`Finished` is ordinal 4, 2026-10-11) — the earlier `31 × (31 × hash + kind) + day` gave Midday of day *d* and Deadline of day *d* + 31 the same id in a cohort of 32 days or more. Both channels are created, and their names and descriptions refreshed (`createNotificationChannel` on an existing channel changes only those), when `ReminderScheduler` is constructed at the app's start, so they are in the phone's settings before the first reminder.
  - **A day done here and not on chain** *(added 2026-10-11, FR-068, product owner)*: a **standing notice** (`Reminder.Kind.NotSent`, tick 0) — "Day N is done, but not on chain yet · open Holdout and submit it" — silent, `setOngoing`, with `setTimeoutAfter` to the deadline. It is not an alarm: `ReminderScheduler.sync` posts it whenever the schedule holds it and it is not in the shade, so it is there at once when the sitting ends and again after a restart, and takes it down when the schedule no longer holds it (the day reached the chain, or the deadline passed). From Android 14 a member may swipe an ongoing notice away; the next sync or hourly re-post restores it. Every hour it is **re-posted silently**: ticks 1…24 at `deadline − k × 3 600 s` (only while after the day opened), each the usual two alarms — `setWindow` with a 10-minute window and the `setAndAllowWhileIdle` fallback — so inexact and Doze-tolerant, the same notification id (updated in place, with the time left refreshed). On a day of 12 hours or more they take the place of that day's Midday and Deadline reminders; a shorter day keeps its Deadline reminder (sounding) beside the standing notice, and has no hours to re-post in. The schedule is told which days are done on the phone (`doneOnPhone`: the day's record or a send waiting) and is recomputed when a sitting ends or a send settles, as well as on every chain read. **Alarm budget:** at most `1 + 2 × days` reminders a Holdout (43 for 21 days), two alarms each, plus at most 24 re-posts × 2 for the one day not on chain — about 135 for a 21-day Holdout, against the 500 an app may hold.
  - **At fire time:** the receiver reads the phone's own record (MMKV, data-model §4). A day completed or waiting to submit is still reminded, to be **submitted** — it counts for nothing until it reaches the chain, and a failed submit is exactly when a reminder helps. A day that reached the chain was already cancelled by the app's next sync. *(Changed 2026-09-27: it used to stay silent for a day done on the phone. Amended 2026-10-11: such a day is kept in the shade and re-posted hourly, above.)* A NotSent re-post for a day the phone no longer holds as done posts nothing.
  - **Permission:** `POST_NOTIFICATIONS` (runtime on Android 13+), asked once — at the first join, or the first time the app finds the member already in a Holdout (someone who joined before reminders existed) — with the reason on the stake sheet; declining is remembered and never asked again unprompted.
  - **The finished notice** *(added 2026-10-11, FR-068b, FR-035a, product owner)*: `Reminder.Kind.Finished`, one per Holdout a member has finished (every day on chain, cohort not settled), at `end + Derive.SETTLE_USUAL_SECONDS` (900 s: the crank's 10-minute pass, R12, plus 5 minutes for the pass) — the same instant the settling card counts down to. Set like every reminder (the `setWindow` pair, the deadline window of the cohort's day length) and posted by the same receiver, which **does not read the chain**: it says the claim is *probably* ready. It stays in the schedule only while its time is ahead (`at > now`), so a chain read after it that finds the cohort still unsettled drops it, and one that finds the cohort settled or claimed drops it too — the app is open then and shows the claim. Its receiver-side horizon (`deadline`) is `at + 6 h`: a phone held in Doze still says it later, never a day later. Silent by `Reminders.isSilent` for 12-hour days or more (05:15 UTC is the night in Europe), with sound for the test lobby. When the membership carries `comeback_entitled`, or the league progress last read says this finish earns a comeback refund and no earlier finished, unsettled Holdout of the league would use the record first (`Reminders.comebackExpected`, FR-061a), the text adds *"It should include a comeback refund too."* — no amount, like every reminder. Its own notification id (`notificationId(cohort, Finished, ·)` = `31 × hash − 2`). The kind's ordinal is 4, so the NotSent alarm slots move to `5 + tick` (still under 64); a sync after the upgrade cancels the old ids it no longer wants. The receiver posts nothing while the app is in the foreground — its own card says where settlement stands, perhaps *taking longer than usual*, and a *probably ready* over it would contradict it (PR #58 review). A posted notice is withdrawn when the app sees the cohort settled or the payout claimed (`Reminders.finishedToWithdraw` → `ReminderScheduler.sync(…, withdraw)`), and on disconnect. **Alarm budget:** one more reminder (two alarms) per finished Holdout.
  - **Rejected for the finished notice** *(2026-10-11, product owner)*: **a background chain read** when the alarm fires (posting only if `settled`, retrying every 10 minutes) — truthful, but the reminders' first network use, against FR-068a; and **WorkManager** with a network constraint — survives reboots, but adds a library and `RECEIVE_BOOT_COMPLETED`, both avoided above.
- **Reboots:** `ELAPSED_REALTIME` restarts with the phone and a chain reading is valid for one boot only (R7), so alarms are not restored by a boot receiver; they come back the next time the app reads the chain (FR-068a). No `RECEIVE_BOOT_COMPLETED`.
- **Rationale:** it is the whole of what a member needs — "you're on, and today isn't done" — with nothing new trusted, stored or sent: constitution X holds (no data leaves the device), the build stays server-free, and chain time stays the only clock.
- **Alternatives considered:**
  - **Firebase Cloud Messaging or any push service:** a server that knows each member's cohort and deadline, plus Google Play services — against the server-free build, for the same messages.
  - **WorkManager periodic work:** a 15-minute minimum period and no timing guarantee; fine for a daily nudge, too loose before a one-hour test day's deadline.
  - **Exact alarms:** a settings-screen permission for a convenience; rejected (above).
  - **A foreground service for the not-sent notice** *(2026-10-11)*: the one way to make a notice un-swipeable on Android 14, but it needs a foreground-service type, a permission and a running process to remind someone of a courtesy; rejected for an ongoing notice that the hourly re-post restores.
  - **Keeping the sounding halfway reminder for a day done here** *(2026-10-11)*: the owner asked for silence every hour, not a second sound; a day done here has already been acted on.
- **Weakness, named in the README:** reminders can arrive a few minutes late, not at all after a reboot until the app is opened, and never if notifications are declined — the deadline is the chain's (constitution XI).

## R22 · The comeback offer, derived on the phone (added 2026-10-11, FR-037g, open item L13; the two-round, 14-day window superseded 2026-10-12 by R24: the next round, or after a last-day miss a late round or the one after; same derivation idea)

- **Decision:** the app works the comeback offer out from the member's forfeited membership the moment the deadline passes, and the program stays as it is. The missed deadline is `deadline_of(days_completed)` of that cohort — the instant `settle_count` later records as `comeback_from` — and the window is `(missed, missed + 14 × day_length]`, the exact test of `LeagueProgress::take_comeback`. The rounds are the league's scheduled starts `first_start + k × cadence` inside the window, so a round not yet opened is still named, with when it opens (at the previous round's start). With weekly cadence and a 14-day window there are always exactly two; the test lobby's short cadence gives more. A round counts as still to open only while joining it will be possible (not inside its own join lock); the test slot takes the rounds of the forfeit's own league (amended 2026-10-12, FR-044a: a test league retired by a newer one still opens the rounds its comebacks need, and while the shared slot records an open pledge the offer follows the pledged league, not a newer forfeit in another test league); and the offer is shown on the latest forfeit's screen only, since a later forfeit replaces it (refined 2026-10-11 after the PR #55 review). A member who joins before automation has recorded the forfeit sends `record_forfeits` for their own pair ahead of `join_cohort` in one transaction, with no running cohort passed to the join.
- **Rationale:** the refund was always earned by joining in time — `settle_count` of the comeback cohort runs after the forfeited cohort is settled (FR-061a), so the forfeit is counted and the window open by then; only the app could not see it, because `progress.comeback_*` is written at settlement, 21 days after a 21-day Holdout started. Deriving it needs no account or instruction change, so H24 is untouched and the fix lands before the submission. The offer and the payout follow one rule, written once in the program and mirrored once in `core`.
- **Why the record goes with the join:** an unrecorded forfeit still holds the profile's running slot, and `join_cohort` refuses an overlap with a running cohort whose end is in the future (`ObligationsOverlap`, 6026). `record_forfeits` is permissionless and idempotent, so sending it first frees the slot in the same transaction; with no running cohort passed, `join_cohort` does not write the old cohort's end back into the cleared slot.
- **Alternatives considered:**
  - **Record the comeback in `record_forfeits`:** the fields exist, so no layout change, but a forfeit recorded mid-cohort and the same forfeit counted again at settlement would both write it, and a later forfeit in the comeback Holdout could be overwritten by the older one's count unless guarded; a program change with LiteSVM tests and a second review the day before the deploy and the submission. Rejected for the devnet build; not needed for the mainnet build either while the derived offer holds.
  - **Wait for settlement, as built:** the offer shows only after joining has closed for most 21-day forfeits (L13).
  - **A refund on any later Holdout, without the window:** changes FR-037e's economics (spec, 2026-10-09 session); rejected by the product owner, rules unchanged.

## R23 · The four-tab shell, the signing flow and Compose tests on the JVM (added 2026-10-11 evening, FR-069…FR-070c)

- **Decision:** (1) **Navigation is a value changed by a pure reducer** — `NavState` (selected tab, one back stack per tab, the open sheet, the signing flow, the sitting) and `reduce(NavState, NavEvent)` in plain Kotlin with no Android types (contracts/android-app.md §5a). `HoldoutApp` renders the state and forwards events; the hub-and-spoke `route` plus `BackHandler` that sent every screen home is replaced. (2) **The wallet-signing flow is a small state machine**, `Waiting → Confirming → Result`, with the mapping from a wallet or chain outcome to a result kind a pure function. It offers **no Cancel**: a Mobile Wallet Adapter session cannot be aborted from the app, and a button that only hid the screen would let the member believe a transaction they may still approve was cancelled. (3) **Compose UI tests run as ordinary JVM unit tests** — Robolectric 4.17 with `ui-test-junit4` in `kotlin/app`'s `src/test`, so the screen and shell tests run in `:app:test*UnitTest` and therefore in `scripts/ci-local.sh`'s Kotlin job, with no device (commit c3ca792). Robolectric is **pinned to SDK 36** in `robolectric.properties`: on 37 Compose's idling fails on a missing `InputManager` method. `compileSdk`/`targetSdk` stay 37; the pin touches only the test runtime. The test JVM opens `jdk.internal.access` (`--add-exports`), which Robolectric needs on JDK 17+. (4) **Two device-local markers** (data-model §4): `looked:{wallet}:{cohort}` for the Standing tab's dot and `sitting:{wallet}:{scope}` for the crash variant of the Stopped screen.
- **Rationale:** the old routing had no tests at all — one composable that needs an Activity and the wallet sender — while the submitted build now has four roots, sheets over them and a flow that must end in the right place for six results. A reducer turns each of those into a table of `(state, event) → state` cases that run in milliseconds; Robolectric covers what the reducer cannot, the screens and the shell, in the gate the project already runs. The signing results are where money and a deadline meet (a join that landed late, a submit after the deadline), so the mapping is tested on its own.
- **Alternatives considered:** Navigation-Compose with a `NavHost` per tab (its back stack is internal state that needs an instrumented or Robolectric run to test, and per-tab stacks with a custom bottom bar are as much code as the reducer); instrumented `androidTest` on a device or emulator (not part of `ci-local`, so a regression would reach the PR gate unseen); screenshot-test libraries such as Paparazzi (a second toolchain for the look, which the design book's hand check already covers); a Cancel on the signing screen that only dismisses it (misleading, above).

## R24 · The guaranteed comeback, and a boost fed by what nobody claims (added 2026-10-12, FR-008, FR-010, FR-027, FR-037, FR-037c–h, INV-1, INV-10)

- **Decision:** (1) A forfeited stake splits **70 / 10 / 10 / 10** — prize pool / the forfeiting member's comeback pledge / developer / operations (operations takes the rounding); no share goes straight to a boost any more. (2) The pledge is **per member**: `record_forfeits` keeps it in the cohort vault as `comeback_due`; `settle_count`, when it counts the forfeit, moves it into the league's reserve vault, books it to `LeagueConfig.comeback_reserve` (open pledges plus refunds owed and not yet drawn) and opens the comeback on the member's `LeagueProgress` (`comeback_stake`, `comeback_league`, `comeback_round` = `first`, `comeback_last_round` = `last`). (3) **The rounds:** `first` is the league's first cohort that *starts* after the missed deadline (smallest `k` with `first_start + k × cadence > missed_deadline`); usually it is still open to join and is the only round (`last = first`). When it is already closed the second after the miss (`missed_deadline + 1 ≥` its join cutoff — exactly a last-day miss) the member chooses: join `first` **late**, until its first day's deadline, or join `first + 1` as usual (`last = first + 1`). (4) **Made good** (counted as a finisher of any index from `first` to `last`; the first one finished uses it): owed `min(10 % of the forfeited stake, the new stake)`, drawn at that cohort's finalization in full and paid with the claim; the excess goes to the boost reserve at once. (5) **Lapsed** — the pledge moves from `comeback_reserve` to `boost_reserve` (no token moves, one reserve vault) — when the member is counted again in the league (a forfeit replaces it; a finish of an index after `last` releases it), or through the new permissionless `release_comeback`, once every round the league has opened is settled (the cohort `min(last, next_index − 1)`) and a round not opened yet is past its first day's deadline. (6) The late join: `join_cohort` takes two optional accounts, `comeback_membership` and `comeback_cohort`, from which it derives the missed deadline and `first`, and lets the member into `first` while it is `Locked` or `Running` until its first day's deadline; a join into a running cohort takes the running slot at once; otherwise a closed cohort stays `JoiningClosed` (6021). (7) The boost is unchanged in size, `min(10 % of the cohort's own pool, boost_reserve)`, and draws only from `boost_reserve`; a cohort nobody finished sends its whole pool to the boost reserve (`no_finisher_boost`). (8) Layout: `LeagueProgress` loses `comeback_from`/`comeback_until` for `comeback_league` (u8), `comeback_round` (u32) and `comeback_last_round` (u32); `Cohort` loses `boost_due`, renames `no_finisher_fee` to `no_finisher_boost`; `settle_count` gains `league` (mut) and `reserve_vault` (mut); `settle_finalize` loses `developer_destination`; two errors, `NoComebackToRelease` (6046) and `ComebackStillOpen` (6047) — the numbers of the two retired carry-over errors, inside the 6040–6047 settlement block, as built. (9) A local ledger reset; nothing is on devnet yet, so the devnet deploy (the owner's call) carries the new layout from its first day.
- **Rationale:** a refund that a shared pot may or may not cover is a hope, not a guarantee. Booking the pledge to the member when the forfeit is counted makes the refund a fixed claim on money nothing else can spend — a boost cannot reach `comeback_reserve`, and other members' refunds cannot draw it down — so there is no pro-rata cut to explain. Counting runs in cohort order (FR-061a), so the booking never depends on the crank's timing; only *when an expired pledge reaches the boost* depends on the crank (INV-10), and a pledge never does. The next round, not 14 days, is one thing to tell a member ("finish the next one") and returns an unused pledge to the boost within weeks, not months. A pool nobody won has no member to refund, and the developer and operations already took 20 % of every forfeit, so it feeds the boost rather than a third payout.
- **Why the rounds start at the first cohort that *starts* after the miss, and why a last-day miss gets a choice:** a member who misses the last day of a round loses at the very second the next round starts (the missed deadline is the second before that start), after its joining closed an hour earlier (`join_lock`) — so "the next round open to join" would silently skip a round they could have played straight away. The late join gives that round back for exactly the day it needs (until its first day's deadline), and the alternative `first + 1` keeps the usual path. Mid-round misses have a still-open next round, so they keep the single round.
- **Why a pledge per member, not a shared comeback pot:** the old pot (5 % of every forfeit, refunds cut pro rata when short) could not promise anything, and a boost sharing a pot with it could spend a member's refund. Per-member booking costs three fields per profile and one more transfer per counting page, and makes INV-10 an equality that the invariant checker can assert.
- **Why `release_comeback` is permissionless, with every opened round and an unopened round's first day in the guard:** releasing too early would spend a member's chance (the late round of a last-day miss is open until its first day's deadline even though joining "closed"; and a finish of the first of two rounds is counted only when that round settles — the time rule alone let a pledge go before that, found in review and fixed in `fe75dfd`); releasing never would strand the pledge and starve the boost. The guard is chain state only — the latest opened round settled, and a round not opened yet past its first day (constitution II) — so any wallet may call it and the crank does (FR-030a, constitution VIII). A repeat call finds no open pledge and moves nothing.
- **Why the late join proves itself with two accounts:** the program must not let any member into a closed cohort; it must be the member's own comeback round. The forfeited (or in-breach) membership and its cohort give the missed deadline from chain state alone, and the cohort's position in the league schedule gives `first`; nothing the caller supplies is trusted (constitution II). The exception to "the roster is final from the join cutoff" (FR-010) is narrow: only that member, only until the first day's deadline.
- **Economics:** a group forfeiting on purpose into its own finisher recovers its 70 % pool part and its 10 % comeback, 0.80 per SKR lost, plus at most the 10 % boost cap on that pool, 0.07, from other members' money: 0.87 < 1 (it was 0.97 under the 20 % refund and the 5 % boost share). A late join adds no money. Comeback money that goes unclaimed makes boosts larger, not the developer's income.
- **Alternatives considered:**
  - **Burn the unused comeback:** rejected. SKR is not our token, so there is no authority to burn it and no right to destroy members' stake value; it breaks "80 % comes back to members" (FR-027); and on devnet, where SKR is a mock mint, it means nothing.
  - **Keep two rounds in a 14-day window with a shared pot and pro-rata cuts:** rejected — not a guarantee (the owner's rule: a member's comeback is never spent by a boost and never cut).
  - **For a last-day miss, only the next round open to join (no late join):** rejected by the product owner — it would skip the round that starts the second after the miss.
  - **Reopen joining for everyone on that round:** rejected — it would break the final roster (FR-010) for all, not just the member whose comeback it is.
  - **Return an expired pledge to the member:** rejected — a missed Holdout would then lose only 20 % instead of 30 %, weakening the stake (and the 0.87 bound).
  - **Record the pledge's league and rounds in `record_forfeits`:** rejected as in R22 — a forfeit recorded mid-cohort and counted again at settlement would both write it; `settle_count` runs in cohort order and is the one place that writes progress (INV-9).
  - **Only the crank may release:** rejected — permissionless is the rule for every step that follows from chain state (FR-030a).
- **Consequences:** the comeback offer of R22 keeps its idea (the app derives the rounds from the forfeited membership and the schedule) but has the new rule and an exact amount; the program, the IDL, the Codama clients, the fixtures, `kotlin/core` and the crank change (tasks, phase 35); `settle_count`'s page size and the record-and-late-join transaction must be re-measured against the legacy transaction limit (S3 figure: 10 pairs; ES-17's record-and-join was 657 bytes of 1232).
