# Contract — Android app (Kotlin)

**Phase 1 output of `/speckit-plan`.** What the native app (`kotlin/app`) promises to the member, the chain and the constitution. What each screen shows and says is fixed by `spec.md`; the screens as built are described in `docs/holdout_screen_map.md` and their look in `docs/design/`. A `PRD §n` citation below names the archived hackathon PRD as a screen's origin only (spec header). This contract fixes the boundaries: permissions, network, storage, wallet use, and which screen shows each state.

## 1. Platform and permissions

| Item | Contract |
|---|---|
| Android SDK levels | min SDK 26, compile/target SDK 37 (Solana Mobile CLI Kotlin Compose Minimal template); primary device Solana Seeker. The JVM Compose tests run under Robolectric pinned to SDK 36 (research R23); that pin changes nothing shipped |
| `CAMERA` | Requested before the first sitting, with the reason stated |
| `RECORD_AUDIO` | **Never declared** in the manifest (FR-022a) — a build check fails if it appears |
| `INTERNET` | Declared; used only as in §2 |
| Merged from the MWA client library | `ACCESS_NETWORK_STATE`, `REORDER_TASKS` and the generated `holdout.app.DYNAMIC_RECEIVER_NOT_EXPORTED_PERMISSION` — all normal, none requested at runtime; read off the built APK with `aapt2 dump badging` |
| `POST_NOTIFICATIONS` | Runtime on Android 13+: asked **once** — at the first join, or the first time the app finds the member already in a Holdout — with the reason on the stake sheet (FR-068). Declining disables reminders and nothing else |
| Other dangerous permissions | None. No `SCHEDULE_EXACT_ALARM` and no `RECEIVE_BOOT_COMPLETED` — reminders are inexact and come back when the app next reads the chain (R21) |

## 2. Network egress

| Destination | Purpose |
|---|---|
| The configured devnet RPC endpoint | Account reads, Clock sysvar, sending signed transactions |
| The configured **names** endpoint (Solana mainnet, `holdout.namesRpcUrl`; spec 003) | Seeker ID lookups for display only (001 FR-063): `getProgramAccounts` and `getMultipleAccounts` on public name records. **And the Seeker Genesis Token check before a join** (FR-003b, R17): `getTokenAccountsByOwner` (Token-2022, `jsonParsed`) for the connected wallet, then `getMultipleAccounts` (`jsonParsed`) on those mints. Nothing else. Sends wallet addresses already public on chain; never a signature, a transaction or device data. Read-only clients that cannot send (003 research R5; `SeekerGenesisReader`) |
| `https://store.solanamobile.com/`, opened in the browser by the member's tap | The Seeker store, linked from the Seeker-exclusive notice (FR-003c). The app makes no request to it itself |
| Local MWA wallet app (Android intents / local websocket) | Authorisation and signing |

Nothing else: the names endpoint is the app's only contact with mainnet, and it only reads. Reminders (FR-068), the finished notice among them (FR-068b), are scheduled and shown on the device and use no network: the finished notice does not read the chain when it fires. Only **Holdout Lab**, the separate tester app (`holdout.app.lab`, spec 004), may save a set's camera as video in its private storage for rep-recognition testing (constitution X v2.1.0, spec 002 FR-026); it never sends it anywhere, and has no network permission at all. The member app contains no recorder in any build. **Camera frames, landmarks and rep traces are never sent anywhere** (FR-022, constitution X); the only rep-derived data leaving the device is the 32-byte `proof_hash` inside `submit_day`. Acceptance criterion 10 is checked by capturing all outbound traffic during a sitting and finding only RPC calls.

## 3. Wallet use (Mobile Wallet Adapter)

Client: `com.solanamobile:mobile-wallet-adapter-clientlib-ktx` 2.2.0, used as in the template — one `MobileWalletAdapter` with a `ConnectionIdentity` (identity URI on our domain with a Digital Asset Links file, icon, name "Holdout") and `blockchain = Solana.Devnet`, and an `ActivityResultSender` created in the activity.

| Action | Client call | Notes |
|---|---|---|
| Connect | `walletAdapter.connect(sender)` | First screen; nothing else is usable before it (FR-001a) |
| No wallet installed | `TransactionResult.NoWalletFound` from any call | Shows the no-wallet screen with how to get a wallet (ES-0) |
| Join, leave, submit completed day, claim | `walletAdapter.transact(sender) { signAndSendTransactions(...) }` | The member's wallet is the fee payer; `Failure` results show a retryable error. While the call is pending the app shows its own signing flow (§5a, FR-070); the session cannot be aborted from the app, so that screen has **no Cancel** |
| Faucet | **none** | Built with `web3-solana`, signed with the bundled sponsor key as fee payer and sent with `rpc-core`; recipient = connected address; no member signature (R13). If the sponsor's float has been emptied and the connected wallet already holds SOL, the same claim is re-sent through `transact` with the member as fee payer — `claim_faucet` accepts either (FR-042b) |
| Reconnect | Stored auth token reused on resume; `connect` again if it was revoked | — |
| Network | Authorized on `solana:devnet` only: the chains the wallet reports for its accounts are checked at `connect` and inside every `transact` before a signature is requested; any other network is refused and the saved token dropped (FR-001b) | A wallet reporting no chains (MWA 1.x) is allowed |
| Disconnect | `walletAdapter.disconnect(sender)` | Returns to the connect screen |

## 4. Device storage

MMKV only, as specified in `data-model.md` §4 (since 2026-10-11 it also holds `looked:{wallet}:{cohort}`, the Standing badge's marker, and `sitting:{wallet}:{scope}`, the sitting-in-progress marker for a crash; since 2026-10-12 `seen:{wallet}`, the day this phone first saw the wallet, for the new-phone banner). Keys are scoped per wallet; switching wallets shows that wallet's own streak and progress. Nothing in storage is trusted by the contract.

## 5a. Navigation, sheets and the signing flow *(added 2026-10-11, evening; FR-069…FR-070c)*

**One pure navigation model.** What is on screen is a value, `NavState`, changed only by a pure function of `(NavState, NavEvent)` in plain Kotlin with no Android types, so every transition is a JVM unit test (research R23). `HoldoutApp` renders the state and sends events (tab selected, route opened, Back, sheet opened or dismissed, signing step reached); it holds no navigation logic of its own.

| Part | Contract |
|---|---|
| Tabs | Four: **Today · Standing · Holdouts · Me**, in that order. The app opens on Today, also when a reminder opens it — and when a reminder's tap reaches the already-running app, which goes to Today (its pushed screens and any sheet dropped, other tabs' stacks kept) without interrupting a sitting or a signature. A reminder's tap lands on Today also when it re-creates an app Android killed; returning to a killed app from the launcher or Recents restores its tab and pushed screens instead (`AppOpen.take(intent, restored)`). Each tab may carry an 8 dp accent dot, never a count, with its meaning also in the tab's accessible name (FR-069; below). The selected tab and each tab's pushed screens survive rotation and the process being killed behind the app (FR-069e; the *Restore* row) |
| Roots | Today = T1 (no running Holdout) or T2 (a running Holdout the member is standing in: the day, then one crowd strip that opens Standing). Standing = the cohort detail (H4) of the running Holdout — the crowd, with the "your day" strip on top while the member stands in it and the day is open and not on chain — else of the last one the member ran, else the empty state (FR-069b). Holdouts = H0 *My Holdouts*, with the *Running now* section for every wallet (FR-062a); its running card pushes H4 over it (`NavEvent.Open(Screen.Detail)`, 2026-10-12). Me = W1 |
| Bar | Shown on a tab's root only. Hidden on: the sitting (all its sub-screens), connect, no-wallet, the tour, the signing flow, *You're in*, and any screen pushed over a root (lobby, cohort detail from another tab, roster, leaderboards, forfeit, claim, About) |
| Back stack | One stack per tab, kept while the member switches tabs. Back pops the current tab's stack; at the root of Standing, Holdouts or Me it goes to Today; at Today it leaves the app. Roster, Leaderboards, Detail, Forfeit and Claim return to the screen that opened them, not to Today (screen map C11) — so Back from the H4 that H0's running card opened lands on H0 (2026-10-12). Selecting the selected tab pops it to its root. A sitting started from Standing's day strip *(FR-069b, 2026-10-12)* is the new transition Standing → Sitting with the bar hidden, and, like a sitting started from Today, it ends on **Today's root** — one exit, since the done state and the auto-submit live on T2 |
| Sheets | Overlay state on top of the opener, not a route: **stake confirm** (with the Seeker gate's checking / not-a-Seeker / couldn't-check variants as states of the same sheet) and **faucet**. Dismissing (drag down, Back, scrim) returns to the opener unchanged. Short of SKR or SOL, the stake sheet's state moves to the faucet sheet and back to the stake sheet when the faucet is done or dismissed (ES-0a), on the chip the member had picked (`NavEvent.StakeTier` keeps the pick in the sheet's state). The faucet sheet shows "Reading the chain…" and a disabled *Get them* until the snapshot and chain time are read |
| Signing flow | Full screen, no bar, for join, submit day and claim; leave and the faucet show the same states inline. States: `Waiting` ("Waiting for your wallet…", spinner, "Approve or decline in your wallet. Nothing moves until you approve.", no Cancel) → `Confirming` (checklist: Approved in your wallet · Sent to devnet · Confirming · result row) → `Result`. Results: `Success`; `Declined` ("Nothing was sent.", with *Try again*); `Failed` ("The network didn't confirm it.", with *Try again*, or with "Check again in a minute" and no *Try again* when the transaction may still land); flow-specific: `JoiningClosed` (join), `DeadlinePassed` (submit → Forfeit screen), `NotEnoughSol` (→ faucet sheet, then back to the flow's opener). The mapping from wallet and chain outcomes (`TransactionResult`, the confirmation read, the program's `DeadlinePassed` / join-cutoff errors) to a result is a pure function, unit-tested (`TxOutcome.of`, `WalletFailures.of`): an error the wallet itself returns — a refusal (→ `Declined`) or any other wallet error code, including Mobile Wallet Adapter's "not submitted" — means nothing reached the network (`Failed` with *Try again*); a session that broke after the wallet opened (lost connection, timeout) may have sent it (`Failed`, may still land, no *Try again*); `NotEnoughSol` comes from the network's insufficient-funds answer, or from a failure that did not go out while the wallet's balance was below what a transaction costs, never for a send that may still land. *Try again* (`TxOutcome.canRetry`: `Declined`, or a `Failed` that cannot still land) always asks the wallet for a new signature |
| After a result | Join success → *You're in* (then Today or the lobby by its two actions); submit success → Today with the day on chain, also when the submit was signed from Standing's day strip *(amended 2026-10-12, one exit)*; claim success → the claim result (amount, *Done*, and after a Spark or a short test Holdout the real open Habit: *Make it a Habit · 21-day* / *Join the next Habit · 21-day*); any other result → its own screen, with Back to the opener. A result message belongs to the screen and the action that produced it and is cleared when the member leaves that screen or another flow starts (FR-070a, amended 2026-10-12) |
| Restore | After the process is killed the app, returned to from the launcher or Recents, comes back on the same tab with the same pushed screens (lobby, detail, roster, forfeit, claim, leaderboards, About; a Holdout by its address). Not restored: a sheet, the signing flow, a sitting, the tour. Saved as plain strings (`nav/NavSaved.kt`, version `v1`); a state that cannot be read lands on Today; so does a reminder's tap that re-creates the app (FR-069, FR-069e) |
| Full-screen exits | The sitting returns to Today's root, also when it was started from Standing's day strip *(amended 2026-10-12)*; the Stopped screen (anything banked or discarded this sitting) returns there on dismiss; stopping with nothing at all goes straight back. The phone's Back in a sitting is the ✕ (the Stopped path above): with the set-up guide or the pre-flight tip sheet open it closes that first (the guide keeping a ticked "Don't show this again"); on a finished day it is the finish button |

**Device-local markers this adds** (data-model §4): `looked:{wallet}:{cohort}` — the number still standing in the Holdout when the member last had its detail on screen; Standing's tab shows its dot, with how many dropped in its accessible name, while fewer are standing now than then (a Holdout never looked at counts from the number who started; FR-069). Only Standing needs a stored marker: the other three dots are derived from state already read — Today while today's reps are not done, Holdouts while a claim is waiting, Me while SKR or SOL is too low to stake or submit. `sitting:{wallet}:{scope}` — written when counting starts, cleared on every clean exit (stop, completion, leaving the foreground); if it is found set at the next Today (read and cleared there, once), the app crashed or was killed mid-sitting, and the Stopped screen's crash variant says what was kept (ES-1, ES-2: the banked blocks).
